Compared with a Makefile for compiling non-kernel driver code, two points may be confusing:

  1. What is KERNELRELEASE?
  2. When is obj-m := module executed?

In fact, make runs twice here: once on the Makefile in the current directory and once on the Makefile in /usr/src/linux. KERNELRELEASE is not defined in the current directory, so the statements under else are executed. When make is run without arguments, it executes the contents of default by default. In the default statement, make -C switches to the kernel source directory and reads the Makefile there. M=${PWD} tells make to return to the current directory and read its Makefile again from the beginning, compiling kernel source files to generate the corresponding .o files. When returning from the kernel source directory, KERNELRELEASE has already been defined, so make reads the content before else and combines the intermediate files to generate the .ko file. After compilation, run insmod module.ko to load the kernel module, use rm module to remove the module, and use dmesg to inspect kernel messages to determine whether the module was loaded or removed successfully.

After running make in the current directory, a series of files is generated: device.ko device.mod.c device.mod.o device.o modules.order Module.symvers. Then run sudo insmod device.ko to load the module into the kernel and use dmesg tail to display recent Linux kernel messages. If the output is Module start, the module was loaded successfully. Afterward, use sudo rmmod device to remove the module and dmesg tail again to display recent Linux kernel messages. If the output is Module end, the module was removed successfully.

DMA Fundamentals

DMA is generally a driver used in kernel space; using it in user space is more complicated.

There are two types of DMA: Slave-DMA and Async TX:

  1. Slave-DMA: memory->device, device->memory, device->device

    The term slave refers to the device participating in the DMA transfer; the corresponding “master” is the DMA controller itself.

  2. Async TX: memory->memory

Here, I mainly introduce how to use slave DMA in the following five steps. For details, refer to the Xilinx DMA slave API:

  1. Request a DMA channel

    A DMA channel (structure: struct dam_chan) is provided by a DMA controller (provider) and used by a consumer (client, driver, slave driver). The client requests a channel through the struct dma_chan *dma_request_chan(struct device *dev, const char *name) API and releases the channel through the void dma_release_channel(struct dma_chan *chan) API.

  2. Configure DMA channel parameters

    After obtaining a DMA channel, the driver configures the channel according to the actual conditions and the capabilities of the DMA controller. It passes struct dma_slave_config to the DMA controller through the int dmaengine_slave_config(struct dma_chan *chan, struct dma_slave_config *config) API.

    The parameters in the code are described below:

    direction: specifies the transfer direction: memory->device, device->memory, device->device, memory->memory

    src_addr: the location from which data is read (no configuration is needed when src is memory)

    dst_addr: the location to which data is written (no configuration is needed when dst is memory)

    src_addr_width and dst_addr_width: the widths of the src/dst addresses

    src_maxburst and dst_maxburst: the maximum burst sizes that can be transferred for src/dst (the amount of data that the DMA controller can buffer)

    device_fc: the module that determines whether a DMA transfer has ended

    slave_id: the slave uses slave_id to tell the DMA controller its identity. This is generally unnecessary; only src, dst, and len need to be known.

  3. Obtain a transfer descriptor

    Obtain the dma_async_tx_descriptor descriptor through the dmaengine_prep_slave_single() API.

  4. Start the transfer

    After obtaining the transfer descriptor, use the dmaengine_submit API to place the descriptor in the transfer queue. It returns a cookie that uniquely identifies the descriptor. Then call the dma_async_issue_pending API to start the transfer.

  5. Wait for the transfer to complete

    Use the dma_async_is_tx_complete() API to determine whether the DMA transaction has completed.
