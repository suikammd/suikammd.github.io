    Lexical and Syntax Analysis with ANTLR
    2020-10-10|

    Recently, I have often worked with ANTLR. At first, I only half understood it and got things to work through all kinds of blind trial and error. After finishing that work, I wanted to systematically understand what a compiler frontend actually does: what lexical analysis and syntax analysis do, as well as the syntax of ANTLR lexers and parsers.

    What Does a Compiler Frontend Actually Do?

    From a fairly high-level perspective, a compiler frontend processes a string in two steps. The first step is lexical analysis, which parses the string into a sequence of tokens. The second step is syntax analysis, which matches the corresponding grammar rules according to the grammar.

    1. Lexical analysis

      Take the SPL query search id |stats count by id as an example. Lexical analysis parses this string into the token sequence search, id, stats, count, by, and |, while also obtaining the type corresponding to each token.

    2. Syntax analysis

      The result of lexical analysis serves as the input to the parser. After syntax analysis, the AST for this SPL query is determined.

      (2) Understanding grammar keywords: ANTLR lexer syntax

      • skip

        skip tells the lexer to discard the currently matched token and read the next one. For example, when defining a custom grammar, there will inevitably be many spaces. These spaces have no actual meaning, so if you do not want to handle them specially, you can skip them.

      • more

        I rarely use more. Roughly speaking, it does the opposite of skip: when more is encountered, it tells the lexer to read another token.

        When it encounters ", I tell the lexer that more tokens need to be matched, while also using mode to enter STR mode.

      • mode(x)

        mode creates a new namespace, which can resolve conflicts with other modes. After entering the new namespace, you can use lexer rules defined in other namespaces.

        With this syntax, after entering the NEWSPACE namespace, you can reuse WHERE, which is defined in another namespace.

      • pushMode(x)

        Enter a new namespace.

        At this point, the lexer enters the new namespace INSIDE.

      • popMode(x)

        Exit the current namespace. If you write popMode directly, you return to the previous namespace. You can think of pushMode as continually pushing onto a stack, with the element at the top of the stack representing the current namespace.

      • type(x)

        This solves the problem of using tokens with the same name in different namespaces. Refer to the description of mode(x).

      • channel(x)

        When I use my defined grammar to write SPL, I do not care about things such as comments and spaces. In this situation, comments and spaces can be routed to different channels. Tokens produced by parsing the source file enter the default channel.
