Rate Limiter
2020-12-11|

Rate limiters primarily prevent highly concurrent traffic from overwhelming a service. Common rate-limiting algorithms include counters, token buckets, and leaky buckets. A token bucket directly rejects requests when there are insufficient tokens, while a leaky bucket blocks requests when there are insufficient requests. This article implements a rate limiter that allows a moderate amount of burst traffic. This is just for fun, so please don’t criticize my crude implementation.

Counter

Counter-based rate limiters are relatively simple: you simply check whether the number of requests in the window has reached the limit. A background process is also needed to reset the request count for the window periodically.

  1. Fixed window

    Limit the number of requests per unit of time. For example, with a QPS of 1k, check whether the count reaches 1k within 1 second. Once it does, reject requests; after 1 second, reset the counter.

    (1) A goroutine is needed to reset the counter every second, using time.Ticker.

    (2) For every incoming request, check whether the counter has reached its limit. If it has, reject the request; otherwise, process it. Concurrent requests must acquire a lock before modifying the counter.

  2. Sliding window

    A sliding window can divide a fixed window more finely. For example, requests over 1 second can be split across 1,000 buckets, with each bucket representing a 1 ms time range.

    (1) Each bucket independently maintains the number of requests in its current time range. When a request arrives, all buckets must be traversed to calculate the total number of requests.

    (2) A scheduled task is needed to remove one bucket and add a new one every 1 ms. A doubly linked list can be used for this, with each bucket corresponding to a node in the list.

Token bucket

As its name suggests, a token bucket works as follows: when a request arrives, it can proceed if it obtains a token; otherwise, it is rejected. Here, I need a background process that periodically puts tokens into the token bucket, ensuring that the token count within the time window always remains at the maximum limit. This is convenient to implement in Go: just use a buffered channel.

Leaky bucket

A leaky bucket can accept a certain amount of burst traffic, but its processing rate is fixed. For example, with a QPS of 1k/s, a scheduled task can put data into a buffered channel every 1 ms, ensuring a fixed processing rate. I won’t implement it here; it can be done by modifying the token bucket implementation slightly.

My implementations above are all fairly rough. The proper way to use a real rate limiter is through RateLimiter.take(): if acquisition succeeds, the request can be processed.

See the code for details: rate-limiter

Mainstream rate limiter implementations

My implementation can be understood as placing tokens on a schedule, while the mainstream approach calculates how many tokens are available when a request arrives. Go’s official extension package github/go/time is based on a token bucket, while Uber’s open-source library is based on a leaky bucket.
