Implementing a Simple Rust Executor
2021-09-28|

Most of this article is based on aysnc-book and explains how to implement a simple executor. The project is available at simple-executor.

Asynchronous programming in Rust involves three important concepts: Future, executor, and reactor. When an executor polls a Future, it passes a waker to the Future. The reactor then waits for the events involved in the Future and, when an event completes, uses this waker to wake the executor so that it can continue executing the Future.

Future

The core of asynchronous programming in Rust is the Future trait. The Future trait has an associated type, Output, which is the result returned when the Future completes. The executor polls the Future step by step until it completes.

When a Future is submitted to the executor, the executor polls it. If it returns Poll::Ready(Result), the Future is finished. If it returns Poll::Pending, the Future needs to be submitted to the executor again the next time it can be polled. This is done by calling Waker’s wake method.

What is a Waker?

When a task is ready to run, the Waker is responsible for waking the task and submitting it to the executor, such as by using Waker’s wake or wake_by_ref methods. The difference is that wake consumes ownership of the waker.

executor

Rust Futures are lazy and can be driven by awaiting them in async functions. So who executes Futures? The answer is the Future executor. The executor polls a Future when progress can be made (for example, when a socket has data to read or is writable). Initially, the executor polls the Future once; subsequently, when the Future can make progress, the wake method submits it to the executor again.

Here, we can first abstract a spawner to handle the initial Future submission. Since a Future itself does not know how to submit itself to the executor, we can encapsulate the Future and its means of interacting with the executor in a Task struct. Instead of submitting a Future directly, we submit a Task. How do we interact with the executor? Again, for simplicity, we use a channel. The spawner holds a reference to the channel’s sending end, and each Task also holds a reference to the channel’s sending end.

At this point, what the executor does becomes obvious: it holds the channel’s receiving end and continually consumes Tasks from the channel and executes them in a large loop.
